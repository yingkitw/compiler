# Benchmark results

Generated by `python3 scripts/bench.py`. Do not edit by hand.

- Host: macOS-27.2-arm64-arm-64bit-Mach-O (arm64)
- CPUs: 8
- Mode: full
- Process spawn overhead (included in every runtime figure): 17.21ms
- Machine load average when the run started: 4.4  (busy host: the runtime ratios are noisy)

Every toolchain compiles the same program and must print the same
result; the harness fails if they disagree. `compute` is the runtime
with the toolchain's own startup cost subtracted, isolating the
workload from process spawn and engine initialisation.

Two of the workloads are the same recursion. `fib` is written the way
a programmer writes it, and our recurrence rewrite fires on it — for
`number` parameters too, since the loop now derives its bound from the
argument's descent. `fib_recursive` is written so that no rewrite can
fire on it, and it is the comparison of what the recursion itself
costs. The `int-fib-rewritten` workload below measures the `int`
variant of the rewrite.

`Compile (cold)` is the first build of that workload and `Compile
(warm)` the second. Each toolchain keeps one cache for the whole run,
so a toolchain that must extract an engine (deno) pays that cost once,
on the first workload only.

## int vs number: recursive calls

The same recursive fibonacci, once with `number` and once with `int`.
This workload is dominated by call overhead rather than by
arithmetic, so it is the comparison that says whether the gap to
scriptc on recursive code is about how calls are compiled or about
floating point.

Both variants use the shape that no rewrite can fire on, so this
compares two recursive programs rather than two loops.

This figure is one run on a shared host, and the difference between
the two variants is small enough to be inside the noise. The
dedicated measurement is `scripts/bench_int.py`, which interleaves
the variants and takes the minimum of many rounds.

| Variant | Artifact size | Runtime | compute |

| `int` (i64) | 33.8 KiB | 68.07ms | 43.36ms |

**The `int` type is 1.03x slower** on this workload.

## What the recurrence rewrite buys

The same fibonacci, twice, both using the `int` type. The only difference is the shape: the first is written so the recurrence rewrite fires on it, the second so that it cannot.

| Variant | Artifact size | Runtime | compute |
|---|---|---|---|
| rewritten into a loop | 33.8 KiB | 24.13ms | 0.00ms |
| left as a recursion | 33.8 KiB | 68.07ms | 43.36ms |

The rewritten program is below the 17ms process-spawn cost, so the comparison is at the measurement's resolution limit. What it shows is that the rewrite removes the recursion entirely: the whole program now costs about as much as starting the process.

The rewrite fires on a `number` fibonacci too — the loop derives its bound from the argument's descent — so the `fib` workload above is no longer exponential on our side either. This section uses the `int` variants so that the two programs differ only in shape: what is measured here is the rewrite, not the type.

## Toolchain notes

- **compiler (current)**: this compiler, built from the working tree
- **deno compile**: bundles the V8 engine into a standalone binary
- **bun build --compile**: bundles the JavaScriptCore engine into a standalone binary
- **scriptc**: statically compiles TypeScript to native code, no engine in the binary
- **compiler v0.1.0 (published)**: the published v0.1.0 of this compiler, for comparison with the current build
- **tsrust + node**: TypeScript 7's Go compiler ported to Rust, emitting JavaScript
- **tsc + node**: reference path: TypeScript to JavaScript, run on the system Node
